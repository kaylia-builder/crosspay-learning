# CrossPay 业务流程与节点架构

> 一份面向学习的跨境支付系统业务流程文档，按时间线和节点拆解每一阶段的业务逻辑。

---

## 一、跨境支付到底"跨"了什么？

国内支付（如微信支付）的链路很短：

```
用户 → 微信支付 → 银行 → 扣款 → 到账
```

整个过程在同一国家、同一清算网络、同一币种内完成。但跨境支付链路：

```
美国买家(USD) → 非洲商户 → 支付平台 → 本地收单行 → 国际清算网络(SWIFT/卡组织)
→ 中间行 → 商户所在国银行 → 商户账户(当地货币)
```

**核心难点**不在"付钱"这一下，而在于：

| 维度 | 国内支付 | 跨境支付 |
|------|---------|---------|
| 币种 | 单一 | 多币种，需汇率转换 |
| 监管 | 单一央行 | 多国监管，合规要求复杂 |
| 清算 | 央行系统 | SWIFT + 中间行，链路长 |
| 时效 | 实时 | T+1 ~ T+5 |
| 费率 | ~0.6% | 2% ~ 5% + 汇损 |
| 拒付/争议 | 简单 | 涉及多国法律 |

## 二、节点架构总览

整个系统围绕一笔跨境支付的生命周期展开，分为 **5 个阶段、7 个节点**：

```
                            ┌──────────────────────────────────────────────────┐
                            │              CrossPay 支付平台                     │
                            │                                                  │
   ┌──────┐                 │  ┌──────────┐      ┌──────────────┐              │
   │ 买家  │─────────────────│─▶│  节点③   │─────▶│   节点④      │──────────┐   │
   │(刷卡) │                 │  │ Payment  │      │  Gateway     │          │   │
   └──────┘                 │  │  Order   │      │  Adapter     │          │   │
                            │  └────┬─────┘      └──────┬───────┘          │   │
                            │       │                   │                  │   │
   ┌──────┐  ①注册          │       │  ②登录验证         │  ⑤回调通知        │   │
   │ 商户  │◄───────────────│───────┴───────────────────┴──────────────────┘   │
   │      │───────────────▶│  ⑥触发结算                                         │
   └──────┘  ⑦收到 97 USD  │       │                                          │
                            │  ┌────▼─────┐    ┌──────────┐                   │
                            │  │ 节点⑥    │    │ 节点⑦    │                   │
   ┌──────┐                 │  │Settlement│    │  Admin   │                   │
   │ 运营  │◄────────────────│──│ Engine   │    │ Console  │                   │
   │ 人员  │                 │  └──────────┘    └──────────┘                   │
   └──────┘                 └──────────────────────────────────────────────────┘
```

### 七个核心节点

| 节点 | 模块 | 职责 | 一句话 |
|------|------|------|--------|
| ① | Auth | 商户注册 + 登录 | 谁有资格用这个平台？ |
| ② | Merchant | 商户身份管理 | 这笔钱最终归谁？ |
| ③ | Payment Order | 支付订单 + 状态机 | 这笔钱现在在哪一步？ |
| ④ | Gateway Adapter | 对接第三方支付渠道 | 实际谁来处理资金？ |
| ⑤ | Callback | 异步结果通知 | 渠道告诉我结果了吗？ |
| ⑥ | Settlement Engine | 结算计算 | 平台抽多少？商户到手多少？ |
| ⑦ | Admin Console | 运营管理 + AI 助手 | 出问题了谁来查？ |

## 三、用户角色

| 角色 | 真实对应 | 核心诉求 | 在 CrossPay 中的功能 |
|------|---------|---------|---------------------|
| **商户 (Merchant)** | 非洲/东南亚的电商网站、SaaS 公司 | 收钱：让海外买家能付款给我 | 注册、看交易、看结算 |
| **买家 (Payer)** | 欧美消费者 | 付钱：用我的信用卡/本地方式支付 | 发起支付（简化：由商户 API 触发） |
| **支付平台运营 (Operator)** | 支付公司内部员工 | 管理：商户、订单、异常处理 | Admin 后台 |
| **支付渠道 (Gateway/Channel)** | 银行、卡组织、本地钱包 | 实际处理资金的管道 | 模拟返回结果 |

> **面试要点**: 面试官问"为什么需要商户系统"时，核心答案是——支付平台不是银行，我们不持有资金，我们服务的是商户。商户入驻 → KYC 审核 → 开通支付能力 → 收单结算，这条链上每一步都要有系统支撑。

## 四、按时间线拆解完整业务流程

### 阶段 1：商户入驻（T-1 日之前）

```
  商户                CrossPay 平台                  数据库
  │                      │                           │
  │  ① POST /api/auth/register                      │
  │  {name, email, password, country}               │
  │─────────────────────▶│                           │
  │                      │  BCrypt 加密密码            │
  │                      │──────────────────────────▶│ INSERT INTO merchants
  │                      │  生成 merchant_no          │
  │                      │  (如 M20240801001)         │
  │                      │◀──────────────────────────│
  │  返回 {token}        │                           │
  │◀─────────────────────│                           │
  │                      │                           │
  │  ② POST /api/auth/login                         │
  │  {email, password}   │                           │
  │─────────────────────▶│                           │
  │                      │  验证密码 + 签发 JWT        │
  │                      │  token 含 {userId, role}   │
  │  返回 {token, merchantNo}                        │
  │◀─────────────────────│                           │
```

**关键点：**
- 密码用 BCrypt 哈希，存 `password_hash`，永不存明文
- JWT 的 `role` 声明嵌在 token 里，后续请求不需要查数据库
- `merchant.fee_rate` 决定后续结算时的平台抽成（默认 3%）

### 阶段 2：发起支付（T+0，实时）

这是整条链路最核心的步骤，涉及 **4 个内部节点 + 1 个外部渠道**：

```
  商户                      CrossPay 平台                               Mock 渠道
  │                            │                                          │
  │  ③ POST /api/payment/create                                         │
  │  {amount: 100, currency: "USD",                                     │
  │   merchantOrderNo: "order-12345"}                                   │
  │───────────────────────────▶│                                          │
  │                            │                                          │
  │                     ┌──────┴──────┐                                   │
  │                     │ PaymentService                                 │
  │                     │                                              │
  │                     │ 1. 从 JWT 解析 merchantId                     │
  │                     │ 2. 验证商户存在且状态为 ACTIVE                  │
  │                     │ 3. 生成平台订单号 PAY20240804000001             │
  │                     │ 4. INSERT payment_orders (status=CREATED)     │
  │                     │ 5. GatewayRouter.route(merchant)              │
  │                     │    └→ 非洲商户 → MockAfricaGateway             │
  │                     │ 6. gateway.pay(req)                           │
  │                     │────────────────────────────────────────────────▶│
  │                     │                                          ┌──────┴──────┐
  │                     │                                          │ 模拟处理:    │
  │                     │                                          │ 80% 成功    │
  │                     │                                          │ 15% 失败    │
  │                     │                                          │ 5%  处理中   │
  │                     │◀─────────────────────────────────────────│ 延时 2-5秒   │
  │                     │  {status: "SUCCESS",                       │ 返回结果      │
  │                     │   channelOrderNo: "AFR-99881"}            └──────────────┘
  │                     │                                              │
  │                     │ 7. order.markSuccess()                      │
  │                     │    - 检查当前状态必须是 PROCESSING           │
  │                     │    - 更新 status=SUCCESS                    │
  │                     │    - 记录 channelOrderNo                    │
  │                     │                                              │
  │  返回 {orderNo, status: "SUCCESS"}                                │
  │◀───────────────────────────│                                        │
```

#### 支付状态机（节点③的核心逻辑）

```
                    ┌─────────┐
                    │ CREATED │  订单刚创建，还没发给渠道
                    └────┬────┘
                         │ gateway.pay() 调用成功
                         │ order.markProcessing()
                         │
                ┌────────▼────────┐
                │   PROCESSING    │  已发给渠道，等待结果
                └────────┬────────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
  markSuccess()   markFailed()    (超时/回调丢失)
          │              │              │
   ┌──────▼──────┐ ┌─────▼─────┐  ┌─────▼─────────┐
   │   SUCCESS   │ │  FAILED   │  │ 保持 PROCESSING │
   └─────────────┘ └───────────┘  │ 等待主动查询/对账│
                                  └────────────────┘
```

**为什么状态机不能直接用 `setStatus()`：**

```java
// ❌ 危险做法——任何地方都能直接改
order.setStatus("SUCCESS");  // 万一从 FAILED 改成 SUCCESS？

// ✅ 正确做法——状态转换被方法守卫
public void markSuccess() {
    if (this.status != Status.PROCESSING) {
        throw new BusinessException("只有处理中的订单才能标记为成功");
    }
    this.status = Status.SUCCESS;
}
```

**双重保险——幂等性：**
如果渠道的回调被重复发送（网络重试），第二次 `markSuccess()` 会因为状态已经是 `SUCCESS` 而不是 `PROCESSING` 直接抛异常，被全局异常处理器捕获后返回 HTTP 200，渠道认为通知成功不再重试。

### 阶段 3：支付回调（T+0，异步）

这是支付系统的"保险丝"——渠道通过异步通知告知最终结果，与同步返回形成双重确认。

```
  Mock 渠道                      CrossPay 平台
  │                                │
  │  POST /api/callback/africa    │
  │  Header: X-Channel-Signature  │  ← 模拟签名验证
  │  {channelOrderNo: "AFR-99881",│
  │   platformOrderNo: "PAY...01",│
  │   status: "SUCCESS",          │
  │   amount: 100}                │
  │───────────────────────────────▶│
  │                                │
  │                         ┌──────┴──────┐
  │                         │ PaymentService
  │                         │
  │                         │ 1. 验证签名
  │                         │ 2. 按 orderNo 查订单
  │                         │ 3. order.markSuccess()
  │                         │    (状态机守卫防重复)
  │                         │ 4. 记录 callbackReceivedAt
  │                         │
  │  HTTP 200                  │
  │◀───────────────────────────│
```

**三种回调场景：**

| 场景 | 渠道返回 | 系统行为 |
|------|---------|---------|
| 正常成功 | `status: SUCCESS` | `markSuccess()` → 订单完成 |
| 正常失败 | `status: FAILED` + `failReason` | `markFailed()` → 记录原因 |
| 重复回调 | 同上（第二次） | 状态机抛异常 → 捕获后返回 200，渠道停止重试 |

### 阶段 4：结算计算（T+1，批量）

这是支付和结算的分界线——**支付模块负责"收钱"，结算模块负责"分钱"**，两个模块完全解耦。

```
  商户/运营                     CrossPay 平台                        数据库
  │                              │                                    │
  │  POST /api/admin/settlement/{id}/complete                         │
  │  (或自动触发日终任务)            │                                    │
  │─────────────────────────────▶│                                    │
  │                              │                                    │
  │                       ┌──────┴──────┐                             │
  │                       │ SettlementService                        │
  │                       │                                          │
  │                       │ 1. 查找该商户所有 status=SUCCESS          │
  │                       │    且未结算的支付订单                      │
  │                       │──────────────────────────────────────────▶│
  │                       │◀──── 返回 10 笔订单，总额 $1,000 ────────│
  │                       │                                          │
  │                       │ 2. 计算费用                               │
  │                       │    totalAmount = 1,000.00                │
  │                       │    feeAmount   = 1,000.00 × 3% = 30.00  │
  │                       │    netAmount   = 1,000.00 - 30.00       │
  │                       │               = 970.00                   │
  │                       │                                          │
  │                       │ 3. 生成结算记录                           │
  │                       │──────────────────────────────────────────▶│
  │                       │  INSERT INTO settlements                 │
  │                       │  {settlementNo, total:1000,              │
  │                       │   fee:30, net:970, status:PENDING}       │
  │                       │                                          │
  │                       │ 4. 关联订单到结算明细                      │
  │                       │──────────────────────────────────────────▶│
  │                       │  INSERT INTO settlement_details           │
  │                       │  {settlement_id → 10个payment_order_id}  │
  │                       │                                          │
  │  返回 {settlementNo, total, fee, net}                             │
  │◀─────────────────────────────│                                    │
```

**结算公式：**

```
NetAmount = TotalAmount − (TotalAmount × FeeRate)

示例: $1,000 − ($1,000 × 3%) = $970 商户实收
```

**分离原则：**

```
         ┌──────────────────────────────────┐
         │  结算模块只读 payment_orders 表     │
         │  绝不 UPDATE 任何支付数据           │
         │  分离 = 职责清晰 + 独立演化          │
         └──────────────────────────────────┘
```

| 维度 | Payment 模块 | Settlement 模块 |
|------|-------------|----------------|
| 时效 | 实时 | T+1 批量 |
| 方向 | 收钱（买家→平台） | 分钱（平台→商户） |
| 频率 | 每笔订单 | 每日一次 |
| 查询模式 | 单行主键查 | 聚合查询（SUM） |
| 对 Payment 表 | 读写 | **只读** |

## 六、模块依赖关系

```
┌────────────────────────────────────────────────────────────────┐
│                        CrossPay Platform                        │
│                                                                │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌─────────┐ │
│   │ Merchant │───>│ Payment  │───>│ Gateway  │───>│ Mock    │ │
│   │ Module   │    │ Order    │    │ Router   │    │ Channel │ │
│   │          │    │ Module   │    │          │    │ Adapter │ │
│   └────┬─────┘    └────┬─────┘    └──────────┘    └─────────┘ │
│        │               │                                       │
│        │               │                                       │
│   ┌────▼─────┐    ┌────▼─────┐    ┌──────────┐                │
│   │ Auth     │    │ Redis    │    │Settlement│                │
│   │ JWT      │    │ Idempot. │    │ Engine   │                │
│   │ Security │    │ Lock     │    │          │                │
│   └──────────┘    └──────────┘    └──────────┘                │
│                                                                │
│   ┌──────────────────────────────────────────────────────┐    │
│   │                   Admin Console                       │    │
│   │   商户管理 │ 订单查询 │ 支付状态 │ 结算报表 │ AI Bot  │    │
│   └──────────────────────────────────────────────────────┘    │
└────────────────────────────────────────────────────────────────┘
```

### 模块依赖原则

- **Auth 模块**独立——认证逻辑不依赖任何业务模块
- **Merchant 模块**不依赖 Payment——商户注册是独立流程
- **Payment 模块**依赖 Merchant（验证商户身份）和 Gateway（发起支付）
- **Gateway 模块**通过 Interface 抽象——换支付渠道不碰业务代码
- **Settlement 模块**读取 Payment 订单数据但不修改——结算和支付的数据职责分离
- **Redis** 承担幂等性锁和缓存，不参与核心业务逻辑

## 七、为什么这些模块缺一不可

| 模块 | 问题 | 答案 |
|------|------|------|
| **Merchant** | 为什么需要商户系统？ | 支付平台服务的对象是商户，不是个人。每家有不同费率、不同结算周期、不同风控规则。 |
| **Payment Order** | 为什么需要订单？ | 订单是支付系统的最小记账单元。没有订单，对账、客诉、风控全都没法做。 |
| **状态机** | 为什么需要状态管理？ | 支付涉及外部系统，网络不可靠、结果可能延迟。状态机确保每一步可追溯、可重试、可补偿。 |
| **Gateway Adapter** | 为什么需要渠道抽象？ | 一个支付平台接的不是一家银行，是全球几十上百家。适配器模式让每个渠道有自己的实现，但对外暴露统一接口。 |
| **Settlement** | 支付和结算的区别？ | 支付是"钱从买家出发"（即时），结算是"钱到达商户"（T+1 或更久）。分离后各自独立演化。 |
| **Admin Console** | 为什么需要运营后台？ | 支付不是无人值守的业务。异常订单处理、客诉查询、商户审核——这些都需要运营人员操作。 |

## 八、每个节点的工程价值（面试要点）

| 节点 | 工程价值 |
|------|---------|
| ① Auth | JWT 无状态设计支撑高并发支付 API，role 嵌入 token 免数据库查询 |
| ② Merchant | 每商户独立费率，后续 KYC/风控/合规都可在此扩展 |
| ③ Payment | 状态机保证数据正确性——非法转换在对象层面就不可能发生 |
| ④ Gateway | 适配器模式——加 Stripe 只需一个新类，零改动 PaymentService |
| ⑤ Callback | 幂等性——重复通知不重复处理，这是支付系统的基本功 |
| ⑥ Settlement | 读写分离——结算读支付数据但不写入，两个模块独立演化 |
| ⑦ Admin | 没有管理后台的支付系统是黑盒——出问题连查都查不了 |

## 九、面试话术参考

> **Q: "你没有支付经验，为什么投我们？"**
>
> A: "确实我之前没有直接参与支付系统开发。但我对这个领域比较感兴趣，通过 AI 辅助学习了支付业务流程，并自己实现了一个简化版跨境支付 Demo。我通过这个项目理解了商户、订单、支付通道、状态管理以及结算之间的关系，也验证了自己快速学习新业务领域的能力。"

> **Q: "支付状态机为什么不能简单只有成功和失败？"**
>
> A: "因为支付不是同步的。调用第三方接口可能 2 秒返回也可能 30 秒返回。PROCESSING 是必要的中间态。此外回调可能丢失——订单卡在 PROCESSING 时需要主动查询来补结果。状态机还提供幂等性保证：如果渠道回调重复发送，第二次状态转换会被守卫条件拒绝，系统返回 200 让渠道停止重试。"

> **Q: "为什么结算要单独一个模块？"**
>
> A: "支付和结算有不同的生命周期。支付是实时的——买家付钱那一刻。结算是 T+1 批量——平台汇总交易、计算手续费、风控审核后才打款给商户。如果把它们放在一个模块，就会把实时系统耦合到批量流程上。另外结算只读支付数据不写入，这是数据完整性的底线。"
